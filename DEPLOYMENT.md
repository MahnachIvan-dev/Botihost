# BotHost — деплой v11

## Архитектура

Рекомендуются **два Railway-сервиса** из одного проекта:

1. **BotHost** — `Dockerfile`
2. **Cashier** — `Dockerfile.cashier`

У каждого сервиса должен быть **1 replica**. Один Telegram polling token нельзя запускать одновременно в двух экземплярах.

## 1. Railway: BotHost

Environment Variables:

```text
BOT_TOKEN=токен основного BotHost
OWNER_ID=твой Telegram ID
OWNER_USERNAME=твой username без @
GROQ_API_KEY=ключ Groq (необязательно, нужен для ИИ-дебаггера)
VERIFIER_BOT=имя кассира без @
SYNC_CHANNEL_ID=-100xxxxxxxxxx
SYNC_SECRET=длинная случайная строка
DATA_DIR=/app/data
```

Подключи Volume:

```text
/app/data
```

## 2. Railway: Cashier

Второй сервис использует `Dockerfile.cashier`.

Environment Variables:

```text
CASHIER_TOKEN=токен кассира
OWNER_ID=тот же Telegram ID
OWNER_USERNAME=тот же username без @
GROQ_API_KEY=ключ Groq
SYNC_CHANNEL_ID=-100xxxxxxxxxx
SYNC_SECRET=ТОЧНО_ТОТ_ЖЕ_СЕКРЕТ
DATA_DIR=/app/data
GROQ_VISION_MODEL=qwen/qwen3.8-27b
```

Для Cashier также нужен Volume `/app/data`, если хочешь сохранять примеры скриншотов между деплоями.

## 3. Закрытый Telegram-канал

Создай приватный канал синхронизации.

Добавь туда:

- BotHost;
- Cashier.

Оба бота должны иметь права администратора, чтобы стабильно получать/отправлять channel posts.

`SYNC_CHANNEL_ID` у обоих сервисов должен быть одинаковым.

`SYNC_SECRET` у обоих сервисов должен быть одинаковым.

## 4. Переменные пользовательских ботов

`.env`-файлы больше **не используются**.

Пользователь открывает:

`Мои проекты → нужный проект → ⚙️ Переменные`

и отправляет:

```text
OPENAI_API_KEY=...
DATABASE_URL=...
MY_SETTING=value
```

BotHost сохраняет эти переменные в своей SQLite БД и передаёт их процессу только во время запуска.

Это удобнее, чем заставлять пользователя создавать `.env` вручную.

## 5. Библиотеки пользовательских ботов

BotHost автоматически создаёт отдельное `.venv` для каждого пользовательского проекта.

Если в проекте есть `requirements.txt`, он устанавливается автоматически.

Если приложение падает с распространённым `ModuleNotFoundError`, BotHost пытается установить отсутствующий пакет автоматически и повторить запуск.

Например:

```text
ModuleNotFoundError: No module named 'openai'
```

→ BotHost автоматически попробует установить `openai`.

Зависимости разных пользовательских ботов не смешиваются.

## 6. Оплата

Путь оплаты:

`BotHost → Тарифы → Оплатить через кассира`

Кассир также умеет начать процесс самостоятельно через `/start` и попросить выбрать тариф.

После выбора тарифа Cashier отправляет в закрытый канал подписанный запрос:

```text
/payment_request USER_ID PLAN USERNAME SIGNATURE
```

После проверки двух изображений:

```text
/payment_result USER_ID PLAN APPROVED GRANT_ID SIGNATURE
```

или

```text
/payment_result USER_ID PLAN REJECTED GRANT_ID SIGNATURE
```

BotHost проверяет HMAC-подпись.

При `APPROVED` слот выдаётся транзакционно и повторный `GRANT_ID` второй слот не создаёт.

## 7. Два скриншота

Кассир просит:

1. скрин чека/успешной отправки Stars;
2. второй скрин профиля/экрана получателя.

ИИ проверяет:

- получателя;
- сумму;
- успешность операции;
- время;
- соответствие двух изображений;
- допустимую разницу времени до 10 минут.

Это AI-проверка изображения, а не прямое подтверждение платежа через официальный платёжный API. Для критичных платежей ручная проверка остаётся возможной.

## 8. Примеры скриншотов

В кассире владелец может отправить:

```text
/set_examples
```

После этого нужно отправить два изображения подряд:

1. пример чека;
2. пример профиля/получателя.

Кассир будет показывать их покупателям перед отправкой своих скриншотов.

## 9. Обновление

Не удаляй Volume `/app/data` при обновлении.

В нём находятся:

```text
bot.db
bots/
payment examples
```

При обновлении просто задеплой новую версию контейнера.

## 10. Важное

Не запускай Cashier вторым процессом внутри BotHost-сервиса.

Не запускай два экземпляра BotHost с одним `BOT_TOKEN`.

Не меняй `SYNC_SECRET` только на одном из сервисов — иначе подписанные сообщения будут отклоняться.
