# BotHost — деплой v9.9

## Архитектура

Рекомендуются **два Railway-сервиса** из одного проекта:

1. **BotHost** — `Dockerfile`
2. **Cashier** — `Dockerfile.cashier`

У каждого сервиса должен быть **1 replica**. Один Telegram polling token нельзя запускать одновременно в двух экземплярах.

## Защита ресурсов Railway

- Оставляй **1 replica** для каждого polling-токена. Не запускай один и тот же токен в двух сервисах одновременно.
- `MAX_PARALLEL_STARTS=1` уменьшает всплеск CPU/RAM при восстановлении многих проектов после деплоя.
- `BOT_MONITOR_INTERVAL=5` позволяет чаще замечать слишком быстро растущие логи; по умолчанию лимит лога проекта — 8 МБ.
- `ARCHIVE_COOLDOWN_SECONDS=2` добавляет паузу между архивами, чтобы массовая архивация не забивала CPU и диск.
- Подключи Railway Volume на `/app/data`. Не размещай несколько сервисов BotHost, которые пишут в одну SQLite-базу, без специально спроектированного общего хранилища.
- Эти лимиты снижают риск перегрузки, но не могут гарантировать отсутствие падений: если запущенные пользователями боты сами потребляют больше RAM/CPU, чем выделено сервису, Railway может завершить контейнер.

## 1. Railway: BotHost

Environment Variables:

```text
BOT_TOKEN=токен основного BotHost
OWNER_ID=твой Telegram ID
OWNER_USERNAME=твой username без @
GROQ_API_KEY=ключ Groq (необязательно, нужен для ИИ-дебаггера)
VERIFIER_BOT=имя кассира без @
SYNC_CHANNEL_ID=-100xxxxxxxxxx
SYNC_SECRET=длинная случайная строка
DATA_DIR=/app/data
MAX_UPLOAD_MB=20
MAX_PROJECT_MB=100
MAX_ZIP_UNCOMPRESSED_MB=100
MAX_ZIP_FILES=500
MAX_TOTAL_BOTS_MB=2048
MIN_FREE_DISK_MB=256
MAX_BOT_LOG_MB=8
BOT_MONITOR_INTERVAL=5
ARCHIVE_COOLDOWN_SECONDS=2
MAX_PARALLEL_STARTS=1
```

Защитные лимиты: файл до 20 МБ, проект до 100 МБ, распакованный архив до 100 МБ, общий объём содержимого проектов до 2 ГБ, лог отдельного бота до 8 МБ по умолчанию (можно изменить через MAX_BOT_LOG_MB). Общий объём и свободное место проверяются перед распаковкой; при достижении лимита существующие данные не удаляются. Если Volume меньше или уже почти заполнен, увеличь его размер или осторожно скорректируй `MIN_FREE_DISK_MB` и `MAX_TOTAL_BOTS_MB`.

Подключи Volume:

```text
/app/data
```

## 2. Railway: Cashier

Второй сервис использует `Dockerfile.cashier`.

Environment Variables:

```text
CASHIER_TOKEN=токен кассира
OWNER_ID=тот же Telegram ID
OWNER_USERNAME=тот же username без @
GROQ_API_KEY=ключ Groq
SYNC_CHANNEL_ID=-100xxxxxxxxxx
SYNC_SECRET=ТОЧНО_ТОТ_ЖЕ_СЕКРЕТ
DATA_DIR=/app/data
GROQ_VISION_MODEL=qwen/qwen3.8-27b
```

Для Cashier также нужен Volume `/app/data`, если хочешь сохранять примеры скриншотов между деплоями.

## 3. Закрытый Telegram-канал

Создай приватный канал синхронизации.

Добавь туда:

- BotHost;
- Cashier.

Оба бота должны иметь права администратора, чтобы стабильно получать/отправлять channel posts.

`SYNC_CHANNEL_ID` у обоих сервисов должен быть одинаковым.

`SYNC_SECRET` у обоих сервисов должен быть одинаковым.

## 4. Переменные пользовательских ботов

`.env`-файлы больше **не используются**.

Пользователь открывает:

`Мои проекты → нужный проект → ⚙️ Переменные`

и отправляет:

```text
OPENAI_API_KEY=...
DATABASE_URL=...
MY_SETTING=value
```

BotHost сохраняет эти переменные в своей SQLite БД и передаёт их процессу только во время запуска.

Это удобнее, чем заставлять пользователя создавать `.env` вручную.

## 5. Библиотеки пользовательских ботов

BotHost автоматически создаёт отдельное `.venv` для каждого пользовательского проекта.

Если в проекте есть `requirements.txt`, он устанавливается автоматически.

Если приложение падает с распространённым `ModuleNotFoundError`, BotHost пытается установить отсутствующий пакет автоматически и повторить запуск.

Например:

```text
ModuleNotFoundError: No module named 'openai'
```

→ BotHost автоматически попробует установить `openai`.

Зависимости разных пользовательских ботов не смешиваются.

## 6. Оплата

Путь оплаты:

`BotHost → Тарифы → Оплатить через кассира`

Кассир также умеет начать процесс самостоятельно через `/start` и попросить выбрать тариф.

После выбора тарифа Cashier отправляет в закрытый канал подписанный запрос:

```text
/payment_request USER_ID PLAN USERNAME SIGNATURE
```

После проверки двух изображений:

```text
/payment_result USER_ID PLAN APPROVED GRANT_ID SIGNATURE
```

или

```text
/payment_result USER_ID PLAN REJECTED GRANT_ID SIGNATURE
```

BotHost проверяет HMAC-подпись.

При `APPROVED` слот выдаётся транзакционно и повторный `GRANT_ID` второй слот не создаёт.

После одобрения кассир дополнительно отправляет BotHost подписанное событие `/payment_audit`. BotHost спрашивает владельца, поступили ли деньги. При ответе «Не оплатил» соответствующие боты пользователя замораживаются, процессы останавливаются, файлы не удаляются. Из-за отсутствия прямой привязки каждого размещённого бота к отдельной подписке текущая безопасная реализация временно замораживает все боты этого пользователя. Владелец может снять заморозку кнопкой в карточке проверки.

## 7. Два скриншота

Кассир просит:

1. скрин чека/успешной отправки Stars;
2. второй скрин профиля/экрана получателя.

ИИ проверяет:

- получателя;
- сумму;
- успешность операции;
- время;
- соответствие двух изображений;
- допустимую разницу времени до 10 минут.

Это AI-проверка изображения, а не прямое подтверждение платежа через официальный платёжный API. Для критичных платежей ручная проверка остаётся возможной.

## 8. Примеры скриншотов

В кассире владелец может отправить:

```text
/set_examples
```

После этого нужно отправить два изображения подряд:

1. пример чека;
2. пример профиля/получателя.

Кассир будет показывать их покупателям перед отправкой своих скриншотов.

## 9. Обновление

Не удаляй Volume `/app/data` при обновлении.

В нём находятся:

```text
bot.db
bots/
payment examples
```

При обновлении просто задеплой новую версию контейнера.

## 10. Важное

Не запускай Cashier вторым процессом внутри BotHost-сервиса.

Не запускай два экземпляра BotHost с одним `BOT_TOKEN`.

Не меняй `SYNC_SECRET` только на одном из сервисов — иначе подписанные сообщения будут отклоняться.


## 11. Дополнительные защитные лимиты

Можно задать следующие переменные Railway (значения по умолчанию показаны справа):

| Переменная | По умолчанию | Назначение |
|---|---:|---|
| `MAX_UPLOAD_MB` | `20` | Максимальный размер одного загружаемого файла |
| `MAX_PROJECT_MB` | `100` | Максимальный суммарный размер проекта |
| `MAX_TOTAL_BOTS_MB` | `2048` | Максимальный общий объём всех проектов на хосте |
| `MIN_FREE_DISK_MB` | `256` | Резерв свободного места, который нельзя занимать загрузками |
| `MAX_BOT_LOG_MB` | `20` | Максимальный размер лога пользовательского бота до обрезки |
| `MAX_ZIP_UNCOMPRESSED_MB` | `100` | Максимальный размер содержимого ZIP после распаковки |
| `MAX_ZIP_FILES` | `500` | Максимальное количество элементов в ZIP |
| `MAX_ZIP_RATIO` | `200` | Верхняя граница коэффициента сжатия для крупных файлов |
| `MAX_ZIP_DEPTH` | `12` | Максимальная глубина каталогов в ZIP |
| `MAX_PARALLEL_STARTS` | `2` | Число одновременных запусков пользовательских ботов |
| `RATE_LIMIT_EVENTS` | `25` | Максимальное число действий пользователя в окне |
| `RATE_LIMIT_WINDOW` | `10` | Окно ограничения действий в секундах |
| `CASHIER_RAW_IMAGE_MAX_BYTES` | `10000000` | Максимальный размер исходного скриншота кассира |
| `CASHIER_IMAGE_MAX_BYTES` | `3500000` | Целевой максимальный размер изображения после сжатия |
| `CASHIER_MAX_CONCURRENT_CHECKS` | `2` | Максимум одновременных AI-проверок чеков |
| `CASHIER_RATE_EVENTS` | `20` | Максимум действий пользователя в окне кассира |
| `CASHIER_RATE_WINDOW` | `10` | Окно ограничения действий кассира в секундах |

Эти ограничения не заменяют лимиты самого Railway. Подбирай их под память, CPU и диск сервиса. После изменения переменных выполни redeploy.

Перед обновлением сделай резервную копию `bot.db` согласованным способом и убедись, что Railway Volume подключён к `/app/data`. Не удаляй Volume и не очищай каталог `bots`.
